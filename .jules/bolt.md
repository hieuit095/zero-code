## 2024-04-03 - Agent Chat Re-render Bottleneck
**Learning:** In `AgentChatter.tsx`, high-frequency WebSocket streaming events (e.g., token-by-token LLM output) caused the entire message history to re-render. Because the `messages` array was mapped inline, every incoming token triggered a full DOM reconciliation for all historical chat bubbles, resulting in an O(N) render cost that degraded performance linearly as the chat lengthened.
**Action:** Always extract items mapped in high-frequency update loops (like streaming logs or chat tokens) into separate components wrapped in `React.memo()`. This creates an O(1) rendering cost where only the actively changing item re-renders, preventing UI stuttering and wasted CPU cycles.

## 2024-05-15 - Recursive Component Re-render Bottleneck in FileTree
**Learning:** In `FileExplorer.tsx`, when `activeTabId` changed, the entire virtual file tree would re-render because `FileRow` components were not memoized. However, simply wrapping `FileRow` in `React.memo()` is only partially effective if it receives a globally active ID (e.g., `selectedId`) as a prop, as a full tree pass is still required to re-evaluate the prop for all nodes. Furthermore, a function scope shadowing issue occurs if the inner memoized function name matches the outer wrapper name, breaking recursion memoization. Passing an inline anonymous function like `(id) => fetchAndOpenFile(id)` breaks memoization entirely because the prop reference changes on every parent render.
**Action:** When memoizing recursive list/tree components, always ensure that callback functions passed down as props are wrapped in `useCallback` to guarantee stable function identity. This works in tandem with `React.memo` to optimize against unrelated parent updates, converting an O(N) cascade into O(1) targeted re-renders.
