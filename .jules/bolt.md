## 2024-04-03 - Agent Chat Re-render Bottleneck
**Learning:** In `AgentChatter.tsx`, high-frequency WebSocket streaming events (e.g., token-by-token LLM output) caused the entire message history to re-render. Because the `messages` array was mapped inline, every incoming token triggered a full DOM reconciliation for all historical chat bubbles, resulting in an O(N) render cost that degraded performance linearly as the chat lengthened.
**Action:** Always extract items mapped in high-frequency update loops (like streaming logs or chat tokens) into separate components wrapped in `React.memo()`. This creates an O(1) rendering cost where only the actively changing item re-renders, preventing UI stuttering and wasted CPU cycles.

## 2024-05-24 - Recursive Tree Component Re-render Bottleneck
**Learning:** In `FileExplorer.tsx`, rendering a deeply nested file tree recursively caused O(N) re-renders whenever a globally active ID (e.g., `selectedId`) changed. Because `React.memo` performs shallow comparisons by default, passing `selectedId` down the tree triggered re-renders for every node, even those whose selection state did not change. This bottleneck degraded performance noticeably in large workspaces.
**Action:** When memoizing recursive components passing a globally active ID, use an anonymous inner function within `React.memo()` (or a separate named function) and provide a custom `arePropsEqual` function. Crucially, ensure that branch nodes (folders) *always re-render* (return `false`) to propagate the active ID down to children, while leaf nodes (files) only re-render if their specific selection state actually toggles. Wrap callbacks passed to memoized children in `useCallback` to prevent breaking the memoization.
